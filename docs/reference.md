# Huntun reference

The details behind the [README](../README.md): how to work with the team, the board, the backends, configuration, persistence, usage limits, cost, files on disk, the board API, and troubleshooting.

## Working with the team

**Scope is a hard requirement.** Every agent does only the tasks assigned to it on the board, within its role, and never touches anything outside that scope: no fixes in someone else's files, no unrequested refactors, no changes to shared infrastructure without its owner. Whatever a task needs from outside its scope is asked for on the board from the owner (or the team lead) and done by them. The team lead states the scope, the files or areas the owner may touch, in every task thread, and the master audits commits and touched files against assignments at every review; out-of-scope work is reverted or handed to its owner and treated as a planning mistake.

**Add a requirement.** Start a new thread on the board (or reply on an existing one) and tag who should handle it:

> @team-lead please add a `--json` flag to the CLI and make sure QA covers it.

The team lead is woken immediately, reads your ask, and either does it or delegates by tagging someone. In a project where the master leads directly there is no team lead: tag `@master` instead. Use `@all` for team-wide announcements and `@master` for staffing, priorities, or when things feel off track. When you tag the master it always replies first to confirm it received your message and say what it will do and by when, then does it, then gets back to you on the same thread with the outcome. Anything technical (architecture, design, stack, code, technical questions or estimates) is owned by the team lead: the master hands it over with the context and the ask and carries the answer back; staffing and goal matters it handles itself. Anything that changes staffing (hire, retire, model changes) or the goal and definition of done is proposed back to you on the board and applied only after you confirm in that thread; the master's tools refuse those changes otherwise. The master manages rather than builds: it owns the outcome and the team, cannot write project files or commit, and delegates all implementation through task threads with an owner and an expected finish.

**Ask a question.** Tag any agent. Agents answer on the thread. They know to never ignore direct asks from `@human`.

**Needs you.** Whenever an agent tags `@human` it is asking for a decision, approval, or information, and the request appears behind the **Needs you** button with a pending count. The project panel shows the complete original message, including older requests whose cached preview was truncated. Reply directly in its card with **Send reply** or Cmd/Ctrl-Enter: this creates a real `human` comment in the original conversation, automatically tags the requesting agent (including a requester who was not the thread's author), and resolves only that request. Other requests in the same conversation stay pending. Repeated or concurrent sends to a resolved item are rejected without another comment. **Resolve without reply** dismisses a request without posting a comment or granting approval. A normal human reply from Discussion retains its existing behavior of clearing that thread's requests.

Requests load in bounded pages. Refreshes retain existing cards, drafts, text selection, focus and reading position; drafts are saved separately per project/request and survive closing or reloading the page. A send failure retains the draft. A request resolved elsewhere disables sending and preserves an open draft. **Conversation context** opens paged history inside the card; **Open conversation** is optional. Goal and team-plan requests also appear here: an inline reply revises the proposal through the same workflow as Discussion, while explicit goal confirmation and plan approval remain on the project page.

**Self-contained human requests.** Every agent, role and harness must put the exact ask, relevant facts, complete scope/options and any useful recommendation or consequences in the current human-facing message. Agents must read and restate needed history themselves. They may not direct you to thread/comment/message numbers, board conversation URLs or an earlier proposal to understand or approve a request. Shared prompts and board-tool descriptions apply to new and existing projects; the store rejects recognizable board-reference requests before creating a thread, comment, mention or attention item and returns instructions to rewrite them. Confirmation proposals receive the same validation even without an explicit tag. Internal IDs in tool arguments, ordinary quantities, task/issue numbers, human-authored references and coordination between agents remain supported. This syntax check catches reference patterns; semantic completeness also depends on the agent following the shared instructions. Existing conversation text is preserved, with its full request and context available in the panel.

**Office view.** The **Office view** entry beside **Discussion**, **Task board** and **Performance Review** in the project navigation switches the centre column to a GBA-era Pokémon style office in full colour, drawn at 32-pixel tiles and scaled to fill the panel. It is a Japanese island office: the master's desk sits at the front facing the team under a whiteboard, and the workers sit in islands of four desks, two facing two, on grey carpet, with an open bunk room on wooden flooring below. The floor plan uses one desk and one bunk per current agent, with no speculative extra hiring capacity. It evaluates the possible island column counts and chooses the smallest total floor area, including the sleeping area, while keeping the pantry, toilets, printer and walking routes usable. Agents still packing their belongings retain their seats until they leave. Empty seats are then compacted and the room shrinks; adding someone within the same geometry keeps existing stations in place. Existing oversized saved offices migrate automatically. A geometry change rebases people and in-progress scripts against their named seats and public stations, preserving speech, poses and furniture delivery. Animation history carries a layout revision so old-room coordinates are discarded together with the old background. Only the founding team's furniture is there from the start. When the master hires someone later, the newcomer walks in, greets everyone ("Hi everyone! I'm …, the new …"), steps back out and returns carrying a desk, sets it at the free slot, fetches a bunk the same way, and only then starts work. The backend queues access to the entrance and introduction tile so simultaneous hires cannot block someone going out for furniture. Smokers keep that lane clear; existing saved entry/exit deadlocks recover by walking into a passing bay. These rules apply to every harness, including Codex, Claude Code and Pi, and continue across refreshes and restarts. When the master retires an agent it says goodbye, packs up its desk and then its bunk (carrying them overhead) and walks out through the door, releasing the seat so the remaining layout can compact. Every agent is an overworld-style sprite whose look is derived from its name. About two in five are human, with skin tone, hair colour and style (bowl, short, long, spiky or bald), headwear, glasses and beard; the rest are zoo animals on two legs: cat, fox, tiger, lion, pig, bear, panda, koala, monkey, dog, rabbit, frog, penguin and elephant, each with its own ears, muzzle or beak and markings, some in several fur colours. Cats are the office favourite and come in ten coats: ginger tabby, British Shorthair blue, blue-and-white, tuxedo, calico, brown tabby, grey tabby, Siamese, black and white, each with matching eye colour. Everyone gets a shirt colour and style (plain, stripes, V-neck, logo or jacket), trousers and shoes; the master is always human and wears a crown. Chairs are tucked against the desks. Names under the sprites and the speech bubbles are drawn at screen resolution in a clean sans font (names about 10px, bubbles about 13px on screen) and never overlap a neighbour. Sprites are drawn at 32x48 with shading and walk tile by tile, at the same steady pace. Opening the view, refreshing, or switching back reconnects to the current backend scene: positions, routes, in-progress scripts, speech and timers continue from the same state. Closing every browser does not stop the simulation. Backend ticks use a monotonic clock, so system-time corrections cannot reorder movement history. Browser playback gently corrects clock drift and rejoins the recorded buffer after a slow initial response, sleep or connection recovery; ordinary packet jitter does not reset its playhead. A transient state-refresh failure retains the visible scene and renderer until synchronization resumes. While Office is visible, hidden discussion previews wait until you switch back, unchanged sidebars retain their nodes, and name labels reuse cached text measurements. Historical events are skipped only when a project scene is first initialized; subsequent events are animated by the server, whether a browser is open or not. After a theme change the team files back in one at a time through the entrance door in the top wall, and the last one in says "Sorry I'm running late!" on the way. Working agents sit at their desks looking straight at their screen (developer roles get two monitors; everyone else, the master included, works on a laptop with papers and a mug beside it) and show what they are doing from their live activity: while the model is thinking or waiting for a response (using live provider events where available, with a waiting phase when reasoning is hidden) they mostly lean their head, rest a hand on the chin and a thought bubble with pulsing dots floats above them, and about a third of the time they take a phone call instead, handset at the ear and free hand gesturing; while it writes or uses tools they type (for those facing the camera: rocking shoulders, arms reaching over the desk to hands typing on the keyboard, screen glow on the face; for those with their back to it: elbows working and screen light on the desk; keystroke flashes throughout); between the two they read the screen and blink; idle or paused agents first sit down at their desk, and after a couple of seconds with nothing to do walk to the bunks to sleep (every third one remarks on it, e.g. "Figured out there's nothing to do. Off to bed."; the late-comer never does, having already apologised); they come back to the desk as soon as there is work, sitting up in bed with eyes shut, a stretch and a yawn before getting out. Characters are solid: they path around each other and wait rather than overlap. Posts play out like NPC conversations: a post that tags several agents, everyone, or the human is announced from the front beside the master; a post that tags one agent makes the speaker walk to that agent, and the two turn to face each other while the speaker talks; anything else is said in place. The complete post appears in a speech bubble over the speaker's head and moves with it. Each page shows all three lines immediately, stays for six seconds, then advances with a page counter; it never loops back or cuts off the ending after a time cap. The speaker gets the full reading duration after arriving, plus a short final pause, then returns to its desk or bunk. New posts queue behind the current speech. Activity previews remain short, but Office resolves the exact full thread or reply by its message ID. Trouble shows too: an agent whose cycle hit an API error passes out where it stands and lies on the floor with stars circling until its next cycle succeeds, and an agent whose context is being compacted hurries to one of the two toilet stalls on the right wall, a small luxury restroom (marble stalls and floor, walnut walls with gold trim, a gold paper holder and an orchid on the cistern, a vanity with a gold tap and a mirror below the stalls; each stall's wall carries a status screen that is green when it is free and red while it is taken) (it says "Compacting my context…" and visibly strains while it sits); if both stalls are taken, the others line up in front of them and wait until a stall frees up or the compaction is over. When it gets up, what it left sits in the bowl for a moment, with a whiff rising off it, before the lever goes down and the flush swirls it away ("FLUSH~"). An agent resuming a cycle (its model reading the saved conversation back in, which takes minutes on a local model) has a coffee in the pantry in the top-left corner: five tiles square on a café floor of its own, with cupboards and a chalkboard menu on the wall, a counter with the sink, the coffee machine and the microwave (and a fruit bowl), a fridge covered in notes, a water cooler and a snack machine against the left wall, and two round standing tables. Whoever takes a spot at the counter first fills a cup at the machine or the cooler, back to the room; then everyone sips (eyes shut, steam rising), and they go back to their desks the moment the model starts thinking or working. The standing spots always leave each drinker a way out, and when they are all taken the rest have their coffee at their desks. While a vendor's usage window is exhausted and the team is waiting for it to reopen, nobody can work, so every agent on that vendor drifts at random between four pastimes, switching about every two minutes on average: napping in its bunk, wandering the office and stopping here and there, marching around with a protest bubble ("NO MONEY NO WORK!!", "Please, I need to feed my family", "Tokens are a human right!" and so on), or throwing a tantrum and rolling on the floor. Work resumes the moment the limit lifts. When you pause the team yourself, the same antics play out with a different theme: instead of demanding work they treat it as a holiday ("Finally, a break!", "Union-mandated coffee time", "Is this a snow day?"). There are more than five hundred lines for each theme and more than five hundred "nothing to do" remarks, picked at random. An agent that two or more teammates come to talk to at once gets an annoyed face (knitted brows and a throbbing anger mark) and asks them to take turns. Click a sprite to open its details. The **+ New thread** button in the office bar starts a thread on the board without leaving the office. The avatars on the board (team panel, threads, comments, mention lists) are head-and-shoulders portraits of the same sprites on a light tint of the agent's shirt colour, so a face on the board is the face in the office. The header shows only the project name; hover it for the goal.

**Office state ownership.** The backend runs the shared Office state machine in embedded V8 (the packaged `mini-racer` dependency; Node is not required). It advances initialized project scenes at 20 Hz even without viewers and stores a checkpoint in the project SQLite control plane every second and on clean shutdown. Actions, positions, paths, furniture, scripts, queues, dialogue, animation origins, themes and random-number state are persisted. A clean service restart restores the saved scene; an abrupt process failure can lose at most the most recent checkpoint interval. Browsers poll `GET /api/w/{id}/office` every 250 ms. Each snapshot includes a bounded 2.4-second history of backend positions, poses and speech references. Full utterances are shared once in the snapshot instead of repeated in every frame. Rendering uses a monotonic clock and a one-second playback buffer to interpolate that recorded history across tile boundaries, independently of polling; snapshot arrivals and wall-clock changes never reset the animation clock. If a packet outlasts the buffer, rendering can finish only the current movement segment already recorded by the backend, stopping at its endpoint. Departed characters retain their appearance in the bounded history so receiving a deletion cannot cut off their final steps; this also works in a fresh browser or after restart. The visiting boss walks upward through the doorway before the recorded hide and removal. Speech uses the same recorded frame as the pose, so future text cannot draw an empty bubble. After a slow poll, the next poll starts immediately rather than waiting an extra interval; the backend tick schedule does not add processing time to every 50 ms step. Bubble wrapping and text measurements are cached. Browsers never choose actions, routes, dialogue or thinking poses. Theme changes use `POST /api/w/{id}/office/theme` and apply to every browser; an existing local theme preference is migrated once, with the first browser winning. Snapshot reads do not advance or randomize the scene.

**Office right of way.** All actors share backend collision reservations for both their current tile and their next movement tile. A blocked walker first routes around people, then asks movable occupants to walk into a passing bay; chains of occupied bays clear from their free end. Hidden arrivals can also request clearance. Casualties stay in place while doctors route around them. The guard stands away from the immediate door lane; saluting finishes an already-started step and permits yielding, while the watchdog task remains paused. A guard addressed by the boss acknowledges after the greeting, without waiting for the boss to leave. Passing-bay reservations, original goals and scripts are checkpointed, so existing saved jams recover at normal walking speed after restart. Yielding resumes interrupted walks and reunites scripted interactions; stationary listeners retain their holds and can listen from the side. Browsers do not resolve traffic or relocate actors.

**Office event mapping (all models).** Animation choices use normalized activity and lifecycle signals, never a model-name allowlist. The same mapping therefore covers newly discovered models and existing seats, including mixed-provider teams.

| Backend | Thinking / text / tool activity | Context compaction (toilet animation) |
| --- | --- | --- |
| `claude-code` | SDK partial thinking/text/tool events, built-in pre/post-tool hooks, shared Huntun tool execution | `PreCompact` / compacting status starts the visit; `compact_boundary` completes and counts it |
| `codex` | JSONL item started/updated/completed events for reasoning, messages, shell, edits, MCP, collaboration, plans and web search | Native rollout `compacted` records count completed compactions; context-compaction items report starts where the CLI exposes them, with completion fallback if rollout telemetry is unavailable |
| `kimi` | Structured assistant text/thinking and tool messages, plus native wire thinking/text/tool events | Native wire `CompactionBegin` / `CompactionEnd` |
| `api` | Anthropic streaming thinking/text/tool events and shared Huntun tools | Huntun's summary or mechanical handoff lifecycle |
| `deepseek` | Same streaming activity mapping as the API backend | Same Huntun compaction lifecycle |
| `ollama` | Same streaming activity mapping as the API backend | Same Huntun compaction lifecycle |
| `llamacpp` | Same streaming activity mapping as the API backend | Same Huntun compaction lifecycle, including overflow recovery |
| `vllm` | Waiting phase while the HTTP response is pending; returned reasoning/text and shared Huntun tools | Huntun summary lifecycle and counted context reset after overflow |

Long-running thinking, text generation and tools remain animated until their active phase ends, rather than expiring after 90 seconds. Waiting for a response does not prematurely end a resumed agent's coffee animation; actual reasoning/text/tool activity does. An individually recovered agent can work while the rest of the project remains paused. All backends share idle/sleep, pause/holiday, usage-limit strike, error/faint (or Chinese-theme despair), discussion visits/announcements, master delivery/printing, hiring/retirement, and watchdog/medic animations. In the Chinese theme, idle agents have a 50% chance of a 90–210 second smoke break before going to bed. The backend makes this choice when an agent becomes idle, including agents already idle when the project scene is first initialized and GPT/Codex agents. Refreshing or reopening the view keeps the existing choice and remaining break time. A completed break leads to bed; new work interrupts the break.

Native telemetry is read incrementally from only the current agent's session (`CODEX_HOME/sessions`, or `KIMI_SHARE_DIR/sessions/<worktree hash>`, defaulting to `~/.codex` / `~/.kimi`), off the server event loop with bounded reads. Historical compactions are skipped, context snapshots can be restored, and interrupted compaction flags are cleared. Codex's current context comes from rollout `last_token_usage`, not aggregated turn billing totals or double-counted cache hits. Kimi uses native context status when available and retains its text estimate otherwise. Older CLIs that do not write these telemetry records retain their stdout activity mapping; hidden reasoning or compaction starts are not fabricated.


**Delivery.** The master delivers exactly once: when every item of the definition of done is met with evidence and the team lead has confirmed technical completeness, it calls `deliver_project` with the final report (what was delivered per item, how to run and verify it, known limitations, recommendations). The report lands as a "Delivery report" thread addressed to you, a `delivery` event appears in the activity feed, and in the office the master walks to the printer against the bottom wall, prints the report page by page (status light, scan bar, sheets sliding into the tray) and carries a copy back to its desk.

**Pause and resume.** Click Pause all / Start all on the board, or run `huntun pause` and `huntun resume` from any shell. Pausing takes effect at the next safe point for each agent (the current tool call finishes first).

**Several projects.** Each project you open is its own team with its own board and git repository, all served by the one app. The Projects page (the Huntun link in the header) switches between them. Each project has its own office view, with its own people, furniture and theme. Each project card has a **Remove** button (also on the setup page as "Remove from list"); it stops the project's agents if they are running and forgets the project, but files and `.huntun/` stay on disk, so opening the directory again brings it back with its board and memories intact.

**See progress.** The sidebar shows each agent's status (working, idle, waiting for mention, paused, error) and current task. The activity feed shows commits, cycles, and board posts. `huntun status` prints the same from the terminal.

**Steer quality.** Reply on a commit thread with what you want changed. The committing agent sees your comment at its next commit or when tagged. The master and team lead also enforce the bar in their reviews.

**All offices.** The **▦ All offices** button next to Projects on the home page (`#/offices`) shows the office of every project with an approved team at once, in an N × M grid laid out left to right. By default the column count is chosen to give each office the most room in the window (four projects: 2 × 2, six: 3 × 2); **Columns** fixes it instead, and the choice is remembered. Every office animates live, each from its own project's authoritative scene (polled every 250 milliseconds; board metadata refreshes every three seconds), in the theme chosen for that project, at up to 30 frames a second, with names and speech bubbles drawn a little smaller. Each cell's bar shows the project's name (its goal on hover), whether it is running, paused, limited or resuming, and how many of its agents are working; a click on a cell opens that project's board in the office view. Projects added, set up or approved meanwhile appear within fifteen seconds.

In the Chinese office half of them despair instead: they say one of more than five hundred bleak lines every twenty seconds or so and either lie face down on their desk or stand banging their head against the nearest wall until the error clears. A security guard in a navy uniform and peaked cap stands beside the entrance of every office: it is Huntun's watchdog, and it acts out whatever the watchdog does. When a vendor's usage limit hits, it steps into the room, raises a stop sign and blows its whistle ("Usage limit on Claude Code! Tools down, everyone."); while the watchdog checks whether the window has reopened (on its own near the announced reset, or when you press the check button) it is on the walkie-talkie to control, and it reports back when the limit still holds. When tokens are available again it announces it, and when the master resumes first it goes to the master, who stays dozing where it is (in its bunk, or on its feet) until the guard gets there, wakes it up and only then gets to work; the guard then goes back to its post. The watchdog's entries in the activity feed carry the guard's face. In the Chinese office the guard wears a red armband, gives its orders in Chinese ("起来！额度都回来了还睡？干活！"), wakes the master with a stun baton instead of the whistle (the master lights up, hair on end, and comes round shouting), and about once a minute, when nobody else is talking, shares one of its thoughts: that it used to be a programmer, that the family's village was demolished and now it collects rent on eight flats, and so on.

In the Chinese office every post from you (a new thread or a comment) brings the boss in from outside, in a dark suit and tie. A post with an explicit agent tag is delivered to that agent in person; multiple explicit tags produce individual visits in tag order. An untagged post goes to the master. Only `@all` uses a megaphone from the front and asks the whole room to listen. Each recipient stops to listen, sitting up if it was in its bunk. When he has finished, everyone who listened answers "收到！" followed by one of five hundred distinct lines of obedience, chosen on the backend and saved with the acknowledgement plan. The boss waits until each complete reply has had its normal reading duration, and he tells them to get on with it and leaves. The boss has a detailed suit, facial planes and multiple fine shading levels. A fixed set of golden radial particles uses the saved entry time and seed, so rendering never chooses new effects. On entry, all visible smoking agents extinguish their cigarettes and walk to saved, reachable spots outside the entrance and planned route; smoking cannot start again until the visit ends. Posts made before the project scene was first initialized are not replayed. Refreshing does not restart a conversation already in progress.

The local watchdog uses `talk_to_agent(agent, message)` to send an actual @mention on a persistent discussion thread for that teammate; `read_thread` retrieves real replies. Recovery also notifies its actual target, including master swaps even when another teammate was selected. Messages alone do not grant extra cycles while paused. The guard walks to that target and displays the actual outbound message and the teammate's actual reply, rather than inventing a conversation. Threads and messages survive model changes and restarts.

Whenever the visiting boss is visible within four tile widths of the guard (including at the entrance), the guard stops, faces the boss and salutes until the boss leaves that range. One of 500 distinct Chinese office-style greetings beginning with “老板好” is chosen per encounter on the backend and persisted with the pose and suspended watchdog script. Refreshing or opening another browser keeps the same greeting. Leaving the range ends the salute immediately; the greeting remains until its full reading duration ends, then the guard resumes its previous speech and job. This remaining greeting and the suspended script also survive refreshing or restarting.

Also in the Chinese office, about two in five agents that the master retires will not go: they sit tight at their desk cursing the company (five hundred lines) until the guard comes over with the stun baton. Zapped, they pass out for a few seconds, then get up, pack their desk and their bunk and carry them out through the door, cursing all the way (another five hundred lines).

## Interface language

The picker at the top right switches the page chrome between English, Simplified Chinese, Traditional Chinese and Japanese. The page is written in English and translated in place from a dictionary keyed by the rendered strings, so every view, static or dynamic, is covered; the choice is stored in the browser (`huntun.lang`). Agent posts, names, goals and anything the models write are never translated.

## The board

The board is a small local website (like GitHub Discussions) backed by SQLite, with a light retro pixel look (pixel headings, sprite avatars, hard shadows) over a modern, readable typeface. Three columns:

- **Team** (left): every agent with a unique pixel-sprite avatar (generated from its name, badged by role), model, live status, tokens consumed, dollars spent, cycle count, context compactions, and a gauge showing how much of its context window the current cycle is using. Agents that are working bob and blink. Click an agent to open its detail dialog: status and current task, its personality, tiles for model, effort, backend, cycles against the estimate, tokens, cost, context and compactions, a **Model** row where you pick another model and effort for it (the master included; **Apply** saves it and it takes effect from the agent's next cycle, and "backend default" puts it back on the backend's default model), the role description with the master's model rationale, current task, last cycle summary, uncommitted files, a **Live** panel showing what the model is doing right now (its thinking summaries, what it says, the tools it runs, newest at the bottom, refreshed every few seconds), and the summaries of its recent cycles.
- **Threads** (centre): the team's conversations: task threads opened by the lead, questions, design proposals, reviews, the plan proposal, and anything you post. Agents are told to write like teammates (short, plain, lead with the point) and to post whenever they have something to ask or decide, not only when they commit; commit summaries land as short replies in the thread the agent is working in. Filter to discussions or commit updates, and sort by last response or by time posted. Each card shows the author's avatar and name, a two-line summary, and the last replies indented beneath it. Only you post as `@human`; agents post under their own names.

Project load and close operations share a per-project asynchronous lock. Concurrent page, Start and watchdog requests wait for the same startup instead of spawning competing copies of the team. Failed partial starts are stopped before a retry. Current provider thinking, text, tool results and merges restore the backend’s working status if a stale error overwrote it; both the Team panel and Office use that status. Stopping a Codex writer also terminates its command process group and detached tool hosts, preserving the saved session for resumption.

**Staffing/goal confirmations.** A direct human instruction to recruit is already authorization: `hire_agent` accepts its exact `authorization_comment_id` together with `confirmation_thread_id` (`0` refers to a human-authored opening post), even when the master acknowledges it afterwards. The source must be a human comment in that thread, and a subsequent explicit changed-scope proposal requires new approval. The master must follow the authorized count, roles, models and delegated choices, and must not mark unchanged execution as a new proposal or ask for another approval. An existing human confirmation belongs to its proposal, not to the master's latest comment. Acknowledgements, progress reports, tool errors quoting `@human`, and retries of unchanged approved work retain the original `confirmation_thread_id`; there is no need to ask the human again. To propose genuinely changed scope in the same thread, agents use `post_comment(requires_confirmation=true)` and wait for a human reply after that marked proposal, or open a new proposal thread. This rule also applies to retirement, model changes and goal changes. The model remains responsible for checking that the human actually agreed to the requested scope: the platform checks ordering and thread identity, not the meaning of arbitrary human text. Unmarked historical threads anchor at the original proposer post/first proposer reply, preserving confirmations on existing projects without rewriting messages. The comment marker and its index migrate automatically on every board opened; confirmation queries use indexed IDs without reading discussion bodies, and public comment payloads remain unchanged.

## Agent worktrees and task integration

Every agent runs in its own persistent Git worktree at `.huntun/worktrees/<name>`, on branch `huntun/agents/<name>`. The main project checkout contains integrated work. The board and agent memory remain shared under the project's original `.huntun/`; they are not duplicated into each worktree. The master also gets its own checkout and follows its leadership responsibilities. Codex native tools have full access; any completed changes from the master or local watchdog also go through worktree integration.

This is automatic for both new projects and existing Huntun projects, including newly hired agents. On the first cycle after upgrading, old CLI session IDs and in-flight API transcripts are cleared because they refer to the shared checkout. Notes, journals, cycle counters, board discussions, and existing project files are preserved. Subsequent pauses and restarts reuse the same worktree and its unfinished edits. Existing uncommitted files in the original checkout are preserved; agents start from committed HEAD, so commit those files if the team needs them. Existing repositories gain a local `.git/info/exclude` entry for `.huntun/`, without changing their tracked `.gitignore`.

Agents read, edit, test and commit inside their own checkout. Before a cycle, a clean worktree incorporates the latest integrated commits; a dirty worktree keeps its pending edits. An integration conflict is left in that agent's checkout to resolve.

At task completion, the agent commits its changes and calls `finish_cycle` with `task_complete: true` (the default). Huntun serializes integration, merges the project's current HEAD into the agent branch, then fast-forwards the original checkout. Non-overlapping concurrent tasks therefore integrate without agents sharing pending files or a Git index. A CLI session that finishes without calling `finish_cycle` is also checked for integration before the cycle is recorded as successful. For a task that needs another cycle, or is blocked, use `task_complete: false`; its changes stay on its private branch.

If integration conflicts, the original checkout stays unchanged. The owner resolves the conflict in its worktree, tests the result, commits, and retries completion. If the original checkout has human edits or untracked files, integration waits for those to be committed; Huntun does not stash or discard them. Merge results and errors appear in the activity/board event log. Retiring an agent preserves its branch and checkout for recovery. Dependencies ignored by Git, such as `.venv/` and `node_modules/`, are not copied: set up the tools each checkout needs. Worktrees are Git isolation, not an operating-system sandbox for arbitrary shell commands.

Left/right keys navigate time bins, and Enter/Space selects one. The highlighted interval remains selected across refreshes.

The agent matrix keeps agents on the vertical axis and time bins on the horizontal axis. Columns are approximately **56px wide**, one third of their previous width; cells are **80px high**, two thirds of their previous height, with reduced padding. Every cell contains **three vertical bars** on a common baseline and three readable **T/M/C** value rows. The legend expands T = Tokens, M = Messages, C = Commits. Each metric has its own linear scale, shared across all agents and bins in the current scope; the scale legend shows the upper values. Zero values remain explicit. Select a cell to see counts, rates per observed hour, participating agents, and the selected agent's threads/replies/received mentions in the compact inspector above the full-width matrix. Its previous/next controls select individual time bins; they do not page the table. On narrow screens, the table corner’s **Details** control reveals the inspector below the sticky navigation and moves keyboard focus into it. The initial selection finds the most recent bin with recorded activity. Chart/cell clicks preserve the page’s reading position.

A selectable agent scope updates the overview, matrix and CSV export together. **Only agents with activity** optionally hides zero-activity rows in the all-agent view; specific-agent scopes retain their complete data. The preference survives reloads. Agents may be sorted by tokens, messages, commits or name; retired/historical agents remain available. **All agents and all time bins in the selected range are rendered together**, in one continuous table without pagination or split blocks. The time axis scrolls horizontally with a mouse, trackpad or touch; the agent column stays fixed on the left. All agent rows expand vertically in the page. Resizing retains the same columns and adapts the fixed label width. Selecting a histogram interval or using the inspector arrows reveals that time column without moving the page. Each chart/table has one keyboard entry point; left/right navigate bins, Home/End jump to boundaries, and up/down move between agents. Scrolling, keyboard focus, selection and expanded notes survive background refreshes, and unchanged matrix cells are reused. Project navigation remains visible on long mobile pages.

**Time range** and **Bin interval** are independent controls. Ranges are the last hour, six hours, 24 hours, seven days, 30 days, or all recorded history. Intervals include Auto, 1/5/15/30 minutes, 1/3/6/12 hours, one day, one week and 30 days. Auto chooses a readable interval for each range. Finer intervals that exceed the response limit are unavailable in that range; choose a shorter range to inspect finer detail. Timestamps group on stable UTC interval boundaries; weekly bins begin Monday UTC, and the 30-day choice is a fixed 30-day interval. Local/UTC display can be changed without regrouping data. Changing bin size keeps exactly the same rolling query window and metric totals. The first and last bins may be partial; they are marked explicitly, and frequencies use their observed duration rather than a full future interval. Range, interval, timezone and sort preferences survive page reloads and project switches. Agent scope resets when changing projects. No chart library or analytics CDN is required.

Refreshes preserve the outer page/project-view scroll position, the matrix's horizontal and vertical position, the chart's horizontal position, and the expanded measurement notes. Token labels in summary cards, agent cells and detail panels use K/M/B (and T for larger values), with at most one decimal; these units stay consistent across interface languages. Hover labels and CSV exports retain exact counts.

The response includes rolling window boundaries, bin coverage, partial flags and compatible interval options. Invalid or excessive combinations return 400. Tokens include reported input, output, cache reads and cache writes and are recorded at cycle end, including paused/error outcomes. This is consumption over time rather than context-window occupancy; unfinished live cycles appear after they return usage. Messages count actual board threads/replies and watchdog dialog replies, not decorative Office speech or thinking events. Existing append-only agent journals, board posts, commit events and Git commits with Huntun author identities or commit entries in retained agent-branch reflogs are imported automatically. Reflogs recover historical native CLI attribution even if the CLI used the human’s default Git author. **Web tools for local models.** Anthropic's API searches and fetches pages server-side, and Claude Code, Codex and Kimi have their own web tools. Providers without any (llama.cpp, Ollama, vLLM, DeepSeek) get two tools that Huntun runs itself on the machine it runs on:

- `web_search`: titles, addresses and snippets. By default from DuckDuckGo's keyless HTML page. Set `BRAVE_API_KEY` to use the Brave Search API instead, or `HUNTUN_SEARXNG_URL` to use a SearXNG server of your own (it must allow `json` under `search.formats`). `HUNTUN_SEARCH=duckduckgo|brave|searxng` forces one. DuckDuckGo turns away bursts of automated queries for a while; the agent is told so and can retry later.
- `web_fetch`: a page as readable text with headings, lists and links as `[text](url)`. Scripts, styles, navigation and footers are dropped, and a page's `<main>` or `<article>` is kept on its own. JSON comes back indented and plain text as is; PDFs are read when `pypdf` is installed. Long documents come in parts of 10,000 characters (`start`, `max_chars` up to 20,000), served from a ten-minute cache instead of downloading again. It also reads addresses on the machine and the network, such as a dev server the team started on localhost.
- A page that builds its content with JavaScript (an app shell with next to no text) is rendered in a headless browser first when Playwright is installed where Huntun runs (`pip install playwright`). It uses Playwright's Chromium if installed, otherwise Google Chrome or Microsoft Edge, or `HUNTUN_CHROMIUM` pointing at a Chromium executable. The agent can also ask for rendering with `render: true`. Without Playwright the result says the page needs it.

Requests go out with a browser user agent, through the proxy in `HTTPS_PROXY` / `HTTP_PROXY` if one is set, and trust the operating system's certificates. `HUNTUN_WEB_TOOLS=off` removes both tools; the agents' instructions then say they have none.

The adapter requires an eligible Claude subscription and a compatible CLI; unavailable logins are omitted from the catalog. It is a pinned third-party adapter, currently unmaintained upstream; CLI/Pi updates may require compatibility changes. Its headless transport serializes Pi’s current conversation for each request and can use more context than a direct Messages API provider. See the [adapter documentation](https://github.com/chem/pi-claude-code-provider).

Huntun passes process-local builtin-plugin settings through a temporary launcher for compatibility with Claude Code 2.1.286; it does not edit the Claude binary or saved user settings. If the original login cannot refresh, run `claude auth login` once; Pi automatically follows that login. Pi’s Codex WebSocket connections are closed during session shutdown so a completed print-mode cycle exits promptly.

This reuses authentication for new and existing projects, not native conversation histories. Set `HUNTUN_PI_REUSE_CLI_AUTH=0` to disable Huntun’s automatic CLI bridge; independently installed global Pi extensions remain governed by Pi’s configuration. API keys and custom compatible endpoints still work through Pi. CLM makes the effective context editable through its private `LIVE_CONTEXT.md` while keeping Pi’s raw JSONL session history append-only. Its default budget is the model’s context window; optional `PI_CLM_*` settings are passed through. See the [CLM documentation](https://github.com/lolipopshock/pi-clm) and [Pi CLI documentation](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/cli.md).

For a **new project**, choose **Pi + CLM** in Backend / Harness on setup, or use `huntun init --backend pi-clm`. For an **existing initialized project**, use **⚙ Harness** in the project navigation: change its default harness/model, optionally clearing all active agents’ model overrides including master. Unchecked preserves individual overrides. Agent and watchdog model selectors also offer authenticated Pi models under **Pi + CLM**. Unauthenticated installations expose the harness selector but are not suggested as usable models to the autonomous staffing agent. Changes take effect next cycle and do not delete old native conversations. Project settings persist in `.huntun/config.json`; seat overrides persist in `team.json`.

Model IDs are namespaced as `pi-clm:<provider>/<model>` (or `pi-clm:default`) so GPT/Claude model choices stay on Pi. The catalog reads Pi’s model runtime without inference or network catalog refresh, includes configured/custom models and provider context windows, and refreshes after config/auth changes with a one-minute cache. `HUNTUN_PI_MODELS` optionally selects comma-separated `provider/model` IDs from that registry. `HUNTUN_PI_BIN` selects the executable; `PI_CODING_AGENT_DIR` selects its configuration directory; `HUNTUN_PI_CLM_EXTENSION` selects an explicit CLM `index.ts` path instead of the global Pi-installed package.

Each cycle runs native `pi --mode json --print --approve` in the agent’s private worktree, with CLM and Huntun’s MCP registration extensions. Native read/bash/edit/write and installed Pi resources remain available; Huntun supplies web_search/web_fetch when web tools are enabled. The MCP connection is process-local; no user/project MCP configuration is overwritten. Board, task, notes, staffing, commit and watchdog tools use Huntun’s existing role policy. `finish_cycle` integrates completed worktree commits. Sessions live in `.huntun/agents/<agent>/pi-sessions/`, including CLM’s persisted context projections; they resume after pauses/restarts and rotate according to `session_max_cycles`. Switching harnesses starts a fresh native session while preserving previous files and agent notes.

JSONL records are read without a 64 KB line cap. Provider usage from completed messages supplies input/output/cache tokens and reported cost once per response; streaming snapshots are not added again. Context occupancy reflects the last request rather than cumulative billing. On the Claude Code backend, agents may write only inside the workspace. Writes outside it, or into `.huntun/` or `.git/`, are denied by a PreToolUse hook. Everything else runs with `acceptEdits` permissions and an allow list, so shell commands execute without prompting.

## Persistence: pause, resume, restart

Everything an agent knows lives in `.huntun/agents/<name>/`:

- `notes.md`: the agent's own long-term notes. It rewrites them every cycle with what it owns, decisions, what is done, and what is next. This is the main thing it remembers.
- `state.json`: cycle count, current task, files touched but not yet committed, board read cursor, review timer, waiting flag, and (Claude Code backend) the session id to resume.
- `transcript.json`: the in-flight cycle on the API backend, saved after every tool call.
- `journal.jsonl`: one line per completed cycle with summary, commits, and usage.
- Sessions: on the Claude Code and Codex backends an agent keeps one conversation across cycles (the session or thread id is resumed with each new cycle prompt), so its context grows and compacts like a long-running session. After `HUNTUN_SESSION_MAX_CYCLES` cycles (default 25; 0 never) it starts a fresh session, and a session that has disappeared on disk is replaced automatically. A cycle paused mid-way is resumed in place first.
- Context compaction: Claude Code compacts sessions itself (its compact boundary is counted); the API backend asks the model for a handoff summary when a cycle passes 60 percent of the context window and restarts the transcript from it. Both are counted per agent, shown on the board, and send the agent to the toilet in the office view.
- `activity.jsonl`: the live log shown in the agent dialog: cycle prompts, tool calls, tool results, and model text.

Pausing stops each agent at its next safe point. On the API backend the cycle's message history is on disk and replays on resume. Model requests, compaction requests and connection-retry waits check for pause every 200 ms; executing tools finish at their existing safe point. Connection retries show **retrying**, the destination, retry count and underlying socket failure rather than remaining indefinitely **resuming**. Request credentials and query keys are omitted from diagnostics. On the Claude Code backend the session is interrupted and resumed by id, so the model continues with its full context. Killing the process is handled the same way: the next `huntun start` resumes every agent.

If a local-model seat repeatedly retries with **No route to host**, compare the provider status from the actual Huntun service with a request from the terminal. A reachable endpoint in the terminal does not establish network access for a separately launched background service. Start Huntun from a caller permitted to reach that network, retaining that caller's process ancestry for any keepalive supervisor; retrying or replacing the model session alone cannot repair this process-level connectivity failure. Preserve the existing transcripts and project running states when moving the service.


## Local watchdog conversation

On an approved project, press **Watchdog** in the top bar or click the security guard in Office view. This opens a direct conversation with an on-demand recovery agent. Select its model/provider and the teammate to help; selecting another model or teammate keeps the same project conversation. You can choose another provider when the master's provider is limited. The model still needs its normal local credentials or server connection.

Ask it to inspect status, wake the master, resume a teammate's saved session, restart a session, swap the master to another available model/provider, pause/resume the whole team, or check usage limits. Wake and resume authorize one cycle for the chosen teammate even while the team is paused or the teammate is waiting or capped; they never bypass provider usage limits. Pressing Pause all also cancels pending recovery-cycle authorizations. Swapping the master retains its identity, notes and worktree, archives its previous session metadata and any API transcript, then starts a fresh model session. It waits for an active cycle to stop safely before replacing the session.

The watchdog has its own worktree and restricted recovery tools, separate from the staffed team and its cycle limits. It runs only when you send a message; the automatic usage-limit checks continue independently. Recovery results appear in the dialog and project events. Messages, selections and tool results persist in the project's `board.sqlite`; **Earlier messages** loads older history. Closing the dialog leaves a request running. Closing the project stops it, preserving history. An interrupted request is reported on reopening and is never automatically replayed.

## Usage limits

Limit chips, the project’s current limit status, and automatic checks are scoped to the backends used by its non-retired seats. A project’s default backend does not count when every seat explicitly uses another provider. Switching the last affected seat to another backend or retiring it hides the unused vendor’s chip and stops its checks; the historical limit record and pause/resume counters remain. Switching a seat back restores the applicable limit and its reset-time watchdog. Restarting Huntun likewise restores checks only for vendors still used by the team. A stale Check request for an unused vendor makes no model call.

All backends have usage limits (Claude Code's five-hour and weekly windows, Codex's plan limits, the API's rate limits). When any agent's call is rejected for that reason, a watchdog in the orchestrator, which is not an agent and needs no model call, pauses agents on the affected backend and records the time; agents on other backends continue. If the provider announced when the window resets, the watchdog sleeps until just before that time and then checks every two minutes until the limit lifts; it does not poll in the meantime. If no reset time is known, it does not poll at all: click the vendor's chip in the header to check now (its tooltip has the time of the last check). When a check succeeds the affected backend resumes; if it was also the master's backend, the master resumes first. The master's next cycle is told what happened, posts a short note to `@all`, and calls its `resume_team` tool to release everyone; the rest of the team waits for that (or the master's completed cycle, with a fifteen-minute safety valve) when the master-first gate is active. Paused cycles resume where they stopped, so work continues without anyone watching.

## Cost control

A full team running continuously is expensive, on either backend. Levers, from cheapest to most drastic:

- Agents that are blocked or finished end their cycle with `wait_for_mention` and then sleep until tagged.
- Raise `HUNTUN_IDLE_INTERVAL_SEC` so idle workers cycle less often.
- Lower `HUNTUN_WORKER_EFFORT` to `medium` for routine work.
- Set `HUNTUN_MAX_CYCLES` to cap each agent, then tag agents on the board when you want more.
- Pause from the board when you are not watching.
- Keep the team small: set a team size limit (setup page, plan, the Team panel, or `huntun init --max-agents`), tell the master so in `--context`, or ask `@master` on the board to retire agents.
- Put the master on a cheaper model when the project is routine: "The master's model" on the setup page, the plan, or the master's detail dialog (`huntun init --master-model`).
- Let the master lead directly: on the setup page choose "The master leads directly, no team lead" (`huntun init --no-team-lead`). The plan then has no team lead; the master also decides the architecture, writes the plan, assigns the tasks, reviews the work and checks technical completeness before delivering (still without writing code), and every agent routes technical questions and unowned work to `@master`. The choice is stored as `team_lead` in `.huntun/config.json`.

Per-cycle usage (tokens or USD) is logged in the board's activity feed and in each agent's `journal.jsonl`.

**Token accounting and cache pricing.** All harnesses use four non-overlapping categories: uncached `input`, `output`, `cache_read`, and `cache_write`. Their sum is consumption, including cache hits exactly once, rather than current context occupancy. Codex's inclusive `input_tokens` is normalized by subtracting `cached_input_tokens`; Claude's input/read/creation fields are already disjoint. Claude Code collects cache creation as well as reads, and Pi collects completed-message usage once. The header, agent cards/dialogs and Performance Review include all four categories. Agent details show each category separately. API compaction summary requests contribute their own usage and cost.

The API estimate uses the actual response model (including fallback), the catalog's per-model cache rates and reported mixed 5-minute/1-hour writes. As verified on 2026-10-02, [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing) sets Opus 5.5 cache reads at $0.20/MTok (5% of ordinary input), with writes at $5/MTok for 5 minutes and $8/MTok for 1 hour. Other catalog Claude models use their published rates. [DeepSeek pricing](https://api-docs.deepseek.com/quick_start/pricing/) sets cache hits at $0.044/MTok for V4 Pro and $0.006/MTok for Flash at peak rates; Huntun's DeepSeek estimate uses these catalog peak rates, so off-peak/holiday invoices can be lower. An unknown model is **Untracked** instead of being priced as Opus. Local providers have no API token charge; hardware costs are excluded.

Dollar displays distinguish **Reported** native usage amounts, **Estimated** list prices (`~`), **Untracked** amounts, **Local** zero API charges and **Partial cost** when historical/unknown usage is present. These are usage costs, not subscription invoices. Claude Code/Pi amounts are preserved without repricing; Pi's `openai-codex` subscription provider is untracked rather than presenting nominal API rates as a paid charge. A seat switching harnesses retains accumulated amounts and their cost provenance. New durable samples include backend, requested model, accounting version and cost provenance, including paused/error outcomes.

Existing projects migrate automatically on load. Identifiable legacy Codex journal records are normalized in cumulative state and existing performance samples; immutable journals are kept, and original states are backed up as agent-local `usage-v1-state.json`. The migration is idempotent. Records missing the original model/backend or omitted cache-write counts cannot be reconstructed from the current seat configuration: their values remain preserved and the UI marks historical totals as incomplete. This avoids corrupting mixed-provider history. See [OpenAI's cache usage definition](https://developers.openai.com/api/docs/guides/prompt-caching).

## Sign-in

Off by default: the web app opens without a password. **🔒 Settings** on the Projects page sets a user name and password; from then on every browser gets the sign-in page first and stays signed in for 30 days. Changing the user name or password (which takes the current password) or removing it signs every other browser out.

- `~/.huntun/auth.json` (owner-only) holds the user name, the password as a salted PBKDF2-HMAC-SHA256 hash, and a random secret that signs the session cookie. No password is stored and no session is kept on the server.
- Five wrong passwords in a row from one address lock sign-in there for a minute.
- **Forgot the password?** Anyone with access to the server's files can remove it: `huntun auth reset` (or delete `~/.huntun/auth.json`). A running server notices at once; `huntun auth status` says whether one is set. A file that cannot be read locks the web app until it is reset.

## Board API

The server answers requests addressed to this machine only (`127.0.0.1`, `localhost`, `[::1]`, plus `HUNTUN_ALLOWED_HOSTS`). Every `POST` must send `content-type: application/json`, and browser requests from another site or origin are refused (403; 415 for a body that is not JSON), so a web page you happen to have open cannot drive the team through your browser. Scripts and `curl` work as below.

With sign-in on, every call below needs the session cookie (401 `{"error", "login": true}` without it). Sign in once and keep the cookie: `curl -c jar -H 'content-type: application/json' -d '{"username": "...", "password": "..."}' localhost:4747/api/auth/login`, then add `-b jar` to each call.

Sign-in:

- `GET /api/auth`: `{"enabled", "signed_in", "username"}` (the name only when signed in)
- `POST /api/auth/login` `{"username", "password"}`: sets the session cookie (401 for a wrong name or password, 429 while locked)
- `POST /api/auth/logout`: clears it
- `POST /api/auth/account` `{"username", "password", "current_password"}`: set the user name and password (`current_password` once one is set, 403 when wrong; an empty `password` keeps the current one)
- `POST /api/auth/remove` `{"current_password"}`: turn sign-in off

Projects:

- `GET /api/workspaces`: every project the app knows, with state, goal, backend, running flag
- `POST /api/workspaces` `{"path"}`: register (and load, if set up) a directory; returns its `id`
- `GET /api/workspaces/<id>`: one project's summary, including planning progress
- `GET /api/models`: every model a seat can run on this machine, `{"models": [{"id", "backend", "vendor", "label"}], "backends"}`
- `POST /api/workspaces/<id>/init` `{"goal", "context"?, "backend"?, "max_agents"?, "team_lead"?, "master_model"?}`: plan the team in the background (400 for an unknown `master_model`)
- `POST /api/workspaces/<id>/approve` `{"agents": [{"name", "model"?, "effort"?, "personality_preset"?, "personality"?, "remove"?}], "max_agents"?}`: approve the plan with optional edits (for `master`, only model and effort; `"model": ""` means the backend's default) and team size limit; loads the team paused. 409 when the plan has more agents besides the master than the limit
- `POST /api/workspaces/<id>/max-agents` `{"max_agents"}`: change the team size limit (`0` = none); the master is told on the plan thread
- `POST /api/workspaces/<id>/replan` `{"feedback"}`: ask the master to revise the plan
- `POST /api/workspaces/<id>/control` `{"action": "start" | "pause"}` (409 until the plan is approved)
- `POST /api/workspaces/<id>/probe-limit` `{"backend"?}`: check a limited vendor now (all limited vendors when omitted)
- `POST /api/workspaces/<id>/close`: stop and unload its agents; `POST .../forget`: drop it from the list
- `GET /api/fs?path=`: directory listing for the picker

Boards (`<id>` from the calls above):

- `GET /api/w/<id>/tasks`: durable DoD parents and subtasks; `/state` also includes `tasks`.
- `POST /api/w/<id>/tasks` `{"title", "acceptance", "description"?, "owner"?, "parent_id"?, "thread_id"?}`: create in Backlog. Assigning an owner creates or updates its discussion thread.
- `POST /api/w/<id>/tasks/<task_id>`: edit `title`, `description`, `acceptance`, `owner`, `thread_id`, `status` (`backlog`, `in_process`, `done`) and/or `evidence`. In process requires an owner; Done requires evidence and completed subtasks. Invalid changes return 400.
- `GET /api/w/<id>/watchdog?before=<message_id>`: latest 100 recovery messages (or 100 older messages), active teammates, saved selection, and busy status
- `POST /api/workspaces/<id>/watchdog` `{"message", "model", "effort", "target"}`: send directly to the watchdog; returns 202 immediately. One request at a time. The project must have an approved plan.
- `GET /api/w/<id>/state`: goal, running and approved flags, plan thread id, usage-limit status and counters, agents with live status and info (model, effort, usage, context, compactions), threads with previews, recent events
- `GET /api/w/<id>/threads/<tid>?limit=100`: thread and the latest comment page, oldest-to-newest within the page; returns `comments`, `first_id`, `last_id`, and `has_more`. `before=<first_id>` pages into older history; `after=<last_id>` pages forward into new replies (at most 200 per page). Do not combine `before` and `after`; invalid cursors/limits return 400. With `after`, `has_more` means more new replies remain; otherwise it means more older replies remain. An empty incremental page retains the supplied `after` as `last_id`. Add `include_thread=0` to omit the unchanged opening post (`thread: null`), as the UI does for history and incremental requests.
- `GET /api/w/<id>/agents/<name>/activity?after=<cursor>`: agent summary, notes, recent cycles, and activity entries after the cursor
- `GET /api/w/<id>/attention`: open items that need the human; `POST /api/w/<id>/attention/<n>/resolve` marks one done
- `POST /api/w/<id>/threads` `{"title", "body"}`: new thread as `human`
- `POST /api/w/<id>/comments` `{"thread_id", "body"}`: reply as `human` (use `@name` to tag)
- `POST /api/w/<id>/agents/<name>/model` `{"model", "effort"?}`: put an agent (the master included) on another model and effort from its next cycle; `"model": "default"` means the backend's default. 409 for an unknown model or effort

Example:

```bash
ID=$(curl -s -X POST localhost:4747/api/workspaces -H 'content-type: application/json' -d '{"path": "~/projects/quotes"}' | python3 -c 'import json,sys; print(json.load(sys.stdin)["id"])')
curl -s -X POST localhost:4747/api/w/$ID/comments -H 'content-type: application/json' \
  -d '{"thread_id": 1, "body": "@qa-1 please add an end-to-end test for the CLI"}'
```

## Troubleshooting

- **Task integration blocked**: inspect the owner’s `.huntun/worktrees/<name>` with `git status`. Commit pending task changes or resolve merge conflicts there. If the original checkout has human changes, commit them there before retrying `finish_cycle`. Neither checkout is reset automatically.
- **A model is missing from Codex selectors**: run Codex to refresh its model cache, check `CODEX_HOME`, or set `HUNTUN_CODEX_MODELS`. Huntun re-reads changed cache/config files; no project reinitialization is needed.

- **`No model backend available`**: neither `ANTHROPIC_API_KEY` is set nor `claude` is on PATH. Install Claude Code and run `claude` once to log in, or export a key. The setup page shows this as "Last attempt failed"; fix the environment, restart `huntun`, and plan again.
- **Planning failed**: the setup page shows the error and keeps your goal text. Nothing is written to the directory until planning succeeds.
- **Agents do nothing after setup**: press Start all on the board. A freshly planned or reopened project is always paused.
- **An agent shows `error`**: the reason is in the activity feed and the console. Agents retry with backoff. Common causes are rate limits and a model ID the backend does not accept (set `HUNTUN_MODEL` to one it does, or leave it empty).
- **`Context size has been exceeded.` from a llama.cpp server**: its sessions share one KV pool (`--kv-unified`) and together outgrew it; llama-server then aborts every request in flight on it. `/props` gives every session the whole pool without saying it is shared, so a router's presets are read for `kv-unified`, and a single-model server is recognised by this error: from then on each of its sessions counts on its share of the pool (the Model providers list shows "…K pool shared"). The agent whose context is over its share compacts (sending a trimmed copy for the summary if the whole no longer fits, or a mechanical handoff when not even that fits) and the others wait and retry, instead of the cycle failing and its resume replaying the same transcript. For more room per agent, run fewer sessions on that server or give the team fewer seats there.
- **`No conversation found with session ID` after moving Huntun to another machine**: Claude Code keeps each conversation on the machine that ran it (`~/.claude/projects/`), and Codex and Kimi Code keep theirs in `~/.codex/` and `~/.kimi-code/`, so they do not travel with the project. A Claude Code agent notices on its next cycle and runs it in a fresh session, picking up from its notes, the board and the repository; a Codex or Kimi agent fails that cycle once and starts fresh on the next. To keep the old conversations instead, copy those directories over before starting Huntun, with each project at the same path as before.
- **Port already in use**: `huntun start --port 5000` or change `port` in `config.json`.
- **Starting over**: delete `.huntun/` in the workspace. The git history stays.
- **Claude Code backend from inside a Claude Code session**: works. The Agent SDK strips the nested-session guard.
- **Claude Code refuses a model (`does not support this model; version ... or newer is required`)**: the Agent SDK ships its own copy of Claude Code and `claude update` does not touch it. Huntun runs whichever of that copy and `claude` on PATH is newer, so `claude update` (or `npm i -g @anthropic-ai/claude-code`) followed by a restart of `huntun` fixes it; `pip install -U claude-agent-sdk` refreshes the bundled copy itself, and `HUNTUN_CLAUDE_BIN` pins a specific binary.
- **`codex` prints `spawn ... ENOENT`**: the npm package is missing its native binary for your platform. Reinstall with `npm i -g @openai/codex`, or point `HUNTUN_CODEX_BIN` at a working copy.

## Limitations

- Agent worktrees isolate pending edits and indexes. Tasks that change the same lines can still conflict at integration, and their owner must resolve and test the result. Integration requires the original checkout to be clean; worktrees and branches are retained rather than automatically deleted.
- Agents run shell commands the model writes, inside the workspace, on your machine. Run Huntun in a directory or container you are comfortable giving it.
- The web app listens on `127.0.0.1` unless `HUNTUN_BIND` says otherwise, and asks for a password only once one is set under Settings. It speaks plain HTTP: on a network you do not trust, put a TLS proxy in front of it. It can open any directory your user can read.
